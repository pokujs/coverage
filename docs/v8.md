# V8 Coverage Protocol

Reference notes on the V8 coverage data model itself: what V8 records during execution, what it emits, and what shape that emission takes regardless of the runtime hosting it. This document describes the foundation that both Node.js and Deno consume.

It complements [docs/node.md](node.md) and [docs/deno.md](deno.md), which describe the runtime-specific framing on top of this foundation. Where those documents focus on envelopes, file naming, and runtime policy, this one focuses on the per-script payload that is shared across both.

---

## 1. Two interfaces to the same data

V8 exposes coverage through two interchangeable APIs that produce structurally identical output:

- **Inspector protocol**: `Profiler.takePreciseCoverage` over the V8 Inspector WebSocket. Interactive. Used by debuggers, IDE integrations, and tools that want to control when coverage is sampled.
- **Environment-variable-driven dump**: V8 inspects a configured env var on process startup, instruments throughout execution, and flushes the entire coverage state to a JSON file on exit. Fire-and-forget. Used by post-mortem coverage tools.

Both produce the same per-script entries. Coverage instrumentation is enabled at isolate startup. Once enabled, V8 records function and block execution counts continuously until the isolate exits or a snapshot is taken. The two APIs differ only in delivery mechanism, not in semantics.

For the rest of this document, the term "V8 coverage data" refers to the per-script entries produced by either API.

---

## 2. The script entry

V8 emits one entry per script the isolate compiled and loaded:

```jsonc
{
  "scriptId": "...",
  "url": "...",
  "functions": [
    /* one entry per function V8 instrumented in this script */
  ],
}
```

Properties:

- **`scriptId`**: a numeric string identifier assigned by V8 at compile time. Stable within one isolate's lifetime. Not stable across processes or across runs. Not load-bearing for downstream tooling.
- **`url`**: V8's view of the script's location. Conventions vary by runtime (`file://`, `node:`, `ext:`, `https://`). V8 itself imposes no schema. The host runtime decides.
- **`functions[]`**: every function V8 instrumented in this script, in source order. Includes the implicit module wrapper (Section 5).

V8 does not include the script source text in this entry. A separate `Debugger.getScriptSource` call is required when source is needed. The env-var dump format simply omits source entirely.

---

## 3. The function entry

Each entry in `functions[]` describes one instrumented function:

```jsonc
{
  "functionName": "...",
  "isBlockCoverage": true,
  "ranges": [
    /* one or more { startOffset, endOffset, count } ranges */
  ],
}
```

- **`functionName`**: the name V8 inferred for the function. Can come from the source identifier, from an inferred name in assignment context (e.g. `const foo = () => {}` becomes `foo`), or `""` for genuinely anonymous functions and the module wrapper.
- **`isBlockCoverage`**: a flag indicating whether `ranges` includes sub-function block ranges. When `false`, only the outer function range is present. Section 6 expands on this.
- **`ranges[]`**: a sorted array of byte ranges with execution counts. The semantics are detailed in Section 4.

V8 does not record argument lists, return types, decorator information, or any other syntactic detail. Its model is purely "named code region with a hit count".

---

## 4. Range semantics

The most consequential part of the protocol. Misreading it produces silently wrong reports.

### 4.1 Byte offsets

`startOffset` and `endOffset` are byte positions into the script source as V8 compiled it. The range is half-open: `[startOffset, endOffset)`. The first range of every function describes the whole function body.

For source positions to be meaningful, the consumer needs to read the same bytes V8 saw. If the runtime executed transpiled code, the offsets are over the transpiled body, not over any pre-transpilation source. Section 7 returns to this.

### 4.2 Nested ranges

When `isBlockCoverage` is true, the function entry can carry multiple ranges. They are nested by containment:

- `ranges[0]` covers the whole function body.
- `ranges[1..N]` are sub-ranges, each strictly contained in the function body.

Sub-ranges represent blocks where execution deviated from the enclosing block's count. Examples include the body of an `if` branch, a `catch` clause, a ternary arm, or any explicit basic-block boundary V8 tracks.

A consumer determining the count at a given byte position walks the ranges from outermost to innermost and takes the count of the innermost range that contains the position. The outer range's count is the default. Inner ranges override it.

### 4.3 What `count` means

`count` is an integer execution counter. It records how many times the entry point of the range was reached. A few consequences:

- The outer range's count equals the number of times the function (or module wrapper) was invoked.
- An inner range with `count: 0` indicates the block was reached zero times, even though the surrounding function executed. This is what coverage tools surface as "uncovered branch" or "uncovered statement" inside an otherwise-executed function.
- An inner range with `count: 5` inside an outer range with `count: 10` means the outer block was entered 10 times but the inner block only ran 5 times. The inner count is absolute, not a delta.

### 4.4 Range ordering and overlap

Ranges within a function are not strictly ordered by `startOffset` in the protocol contract, although in practice V8 emits them in a consistent order. Tools should not rely on input order for correctness. Re-sorting before walking is safe and recommended.

Ranges within the same function never partially overlap. Two ranges either share no bytes, or one strictly contains the other. This is what allows the "innermost containing range wins" rule of Section 4.2 to work without ambiguity.

## 5. The module wrapper convention

V8 wraps every loaded module in an implicit function. The wrapper appears in `functions[]` as the first entry, with:

- `functionName: ""`
- `isBlockCoverage: true`
- `ranges[0]` covering the entire script body, from offset `0` to the source byte length.

The wrapper's `count` is the number of times the module was instantiated. For typical ES modules, this is `1`. For modules loaded from multiple contexts or through loaders that touch the wrapper before user code runs, it can be higher.

Some runtimes consistently report wrapper counts other than `1`. Deno reports `2` for every TypeScript module, regardless of import count, because of an internal load-then-execute cycle. The wrapper count is a runtime-policy artifact, not a V8-protocol invariant. Tools that interpret it as "how many times the module was imported" can be misled. The reliable signal is "did the module execute at least once", which is `wrapperCount > 0`.

---

## 6. Block coverage vs function coverage

V8 supports two granularities:

- **Function coverage**: each `functions[]` entry has exactly one range, covering the function body. `count` is the invocation count. No information about which paths inside the function executed.
- **Block coverage**: each `functions[]` entry can have multiple ranges, with sub-function blocks reported as nested sub-ranges. `isBlockCoverage` is `true`.

Both Node and Deno enable block coverage by default for their coverage env-var paths. Function coverage exists primarily for sampling-profile use cases where the overhead of block tracking is unacceptable.

In practice, every dump observed in real coverage workflows has `isBlockCoverage: true`. Consumers can assume block granularity, but a defensive implementation honors the flag and falls back to function-level aggregation when it is `false`.

---

## 7. What V8 does not compute

The V8 coverage protocol is intentionally narrow. The following are **not** V8's responsibility:

- **Source maps.** V8 records offsets into the bytes it compiled. If the host runtime ran transpiled code, the offsets are over the transpiled body. Projecting them onto a pre-transpilation source is the consumer's job, using whatever source map the transpiler emitted out of band. V8 does not embed, parse, or apply source maps.
- **Source text.** Not included in the per-script entry. Available separately via `Debugger.getScriptSource` or by reading the file from disk when the URL is `file://`.
- **Function metadata beyond name.** No parameter list, no async or generator flag, no decorators, no class membership.
- **Branch and arm semantics.** V8 reports block counts. Translating those into "this if-arm was covered" or "this ternary alternative ran" is a structural inference based on the source AST, performed downstream.
- **Statement boundaries.** V8 has no notion of statements distinct from blocks. Per-statement coverage is computed by the consumer from line counts plus block boundaries.
- **Per-line counts.** Lines are a source-text concept, not a V8 concept. Line counts are derived by mapping byte offsets to line numbers using the script source.

This is the right division of labor. V8 records what it can know cheaply: counter increments tied to compiled-code regions. Everything that depends on source structure or external metadata happens above V8.

---

## 8. Determinism and runtime parity

For the same input bytes, V8's coverage instrumentation is deterministic. Two runtimes hosting the same V8 build, executing the same script with the same inputs, produce byte-identical `functions[]` arrays for that script.

Direct comparison of dumps emitted by Node.js and Deno against the same JavaScript source confirms this. `functionName`, `isBlockCoverage`, every `startOffset`, every `endOffset`, every `count` matches across the two runtimes for every user file in a mirrored playground.

The implication is that **all observable differences between Node and Deno V8 dumps are framing**: which scripts the runtime chose to instrument, how it packaged the per-script entries into files, what URL scheme it used, whether it shipped a source map alongside the dump. The instrumentation itself is shared.

This determinism is what makes a single, runtime-agnostic V8 pipeline possible. Below the framing layer, there is exactly one V8 to handle.

---

## 9. Operational implications

A few rules that fall out of the model:

- **Trust `count` per range, not per line.** The protocol's unit is the range. Per-line counts are derived. Bugs in per-line aggregation are downstream of V8 and cannot be attributed to it.
- **The innermost range wins.** When computing the count at a byte position, walk ranges from outermost inward and take the count of the innermost containing range.
- **Range geometry is identical for the same URL across processes.** When the same module is loaded by N processes, V8 emits N entries for it with the same `startOffset` and `endOffset` for every range. Only `count` varies. Aggregation across processes is therefore a per-range sum, not a re-projection.
- **Wrapper `count` is not a load count.** It reflects whatever the host runtime's loader does when initializing the module. Use it for "did the module execute at least once" answers, not for import counting.
- **`isBlockCoverage: false` is rare but possible.** Defensive consumers branch on the flag to decide whether sub-function ranges are meaningful or absent.
- **Synthetic functions injected by transpilers are V8-real.** From V8's perspective, an esbuild-injected `__name` helper is a function like any other, with its own range and count. V8 cannot distinguish synthetic from authored. Filtering is a source-level concern handled by the consumer, typically via source-map projection.

---

## 10. Summary

| Axis                 | V8 protocol                                            |
| -------------------- | ------------------------------------------------------ |
| Unit of measurement  | byte range with execution count                        |
| Range semantics      | nested by containment, innermost wins                  |
| Function model       | name, ranges, block-coverage flag                      |
| Module wrapper       | first function entry, `functionName: ""`, spans script |
| Block coverage flag  | per-function, indicates presence of sub-ranges         |
| Source maps          | not V8's concern, host or consumer applies them        |
| Source text          | not in coverage dump, available separately             |
| Determinism          | same bytes in, same `functions[]` out                  |
| Cross-process parity | identical range geometry per URL, only counts vary     |
| Cross-runtime parity | byte-identical `functions[]` for the same script       |

V8's coverage protocol is small, predictable, and agnostic of how it is consumed. Everything specific to a runtime, a transpiler, or a tool happens above it. Understanding this division is what allows a coverage tool to span Node.js, Deno, and any future V8-hosted runtime without internally branching on which one produced the data.
